# 技能名称：spark-sql-standards

## 规范内容

### 一、通用编码风格（基于阿里/腾讯规范）

#### 1.1 关键字与大小写
- **强制**：SQL关键字、保留字统一使用全大写（SELECT、FROM、WHERE、JOIN、GROUP BY等），禁止大小写混用
- **强制**：表名、字段名使用小写字母+下划线分隔（snake_case）
- **推荐**：常量值使用大写（如 STATUS_ACTIVE）

#### 1.2 缩进与换行
- **强制**：使用4个空格作为一个缩进量，所有缩进为1个缩进量的整数倍
- **强制**：SELECT字段按每行一个字段的方式编排，首个字段与SELECT之间缩进1个缩进量
- **强制**：FROM、WHERE、GROUP BY、HAVING、ORDER BY、JOIN等子句换行编写，与SELECT左对齐
- **强制**：WHERE子句中的AND/OR与WHERE左对齐
- **推荐**：运算符（+、-、*、/、=、>、<、AND、OR）前后保留1个空格

#### 1.3 SELECT规范
- **强制**：禁止使用 `SELECT *`，必须明确指定列名
- **推荐**：使用 `EXPLAIN` 命令查看执行计划，确认谓词下推和列裁剪是否生效

#### 1.4 别名规范
- **强制**：表别名必须有意义，避免使用a、b、c等无意义别名，同一查询中别名不可重复
- **推荐**：子查询别名使用分层命名（P1/S1/U1/D1或a/b/c/d），区分嵌套层次
- **推荐**：字段别名使用 `AS` 关键字，与字段在同一行，多字段AS建议对齐

#### 1.5 CASE WHEN规范
- **强制**：CASE语句必须包含ELSE子句
- **推荐**：WHEN子句在CASE语句同一行，缩进1个缩进量
- **推荐**：每个WHEN子句尽量在一行内完成

#### 1.6 注释规范
- **强制**：每条SQL语句均应添加注释说明，注释单独成行，放在语句前面
- **推荐**：代码头部添加主题、功能描述、创建者、创建日期、修改日志等信息
- **推荐**：复杂业务逻辑、魔法值（如状态码）必须添加注释说明

### 二、Spark SQL性能优化（整合大厂实践，适配Paimon表）

#### 2.1 数据存储与格式（Paimon表）
- **强制**：在Paimon表建表语句的 `WITH` 子句中，通过 `'file.format'` 参数明确指定文件存储格式，推荐使用列式存储 `'parquet'` 或 `'orc'`
- **强制**：通过 `'file.compression'` 参数启用数据压缩，默认压缩算法为 `'zstd'`，可根据业务场景选择 `'zstd'`、`'lz4'`、`'snappy'` 或 `'gzip'`
- **推荐**：对于追求极致写入性能的场景，可考虑为不同LSM树层级配置不同文件格式和压缩算法（如 `'file.format.per.level' = '0:avro,1:parquet'`，`'file.compression.per.level' = '0:lz4,1:zstd'`）
- **注意**：Paimon表本身管理数据文件，ETL过程无需显式转换格式，只需在建表时配置即可

#### 2.2 分区策略（Paimon表）
- **推荐**：分区字段选择高基数、查询频繁的维度（如 `dt`、`region`、`product_category`）
- **推荐**：采用“日分区”策略，每日写入独立分区
- **避免**：过度分区（如按小时分区导致数万小文件），会增加Driver元数据负担
- **Paimon特有**：可结合 `'partition.expiration-time'` 自动清理过期分区

#### 2.3 数据倾斜处理
- **推荐**：启用Spark自适应查询执行（AQE）：`spark.sql.adaptive.enabled=true`
- **推荐**：启用倾斜Join优化：`spark.sql.adaptive.skewedJoin.enabled=true`
- **推荐**：对倾斜键使用加盐（Salting）技术：添加随机前缀打散数据后聚合
- **推荐**：对小表（<10MB）使用广播Join：`spark.sql.autoBroadcastJoinThreshold=10485760`，或显式使用 `/*+ BROADCAST(t) */` 提示
- **注意**：Paimon表作为源表时，同样适用上述优化；大模型写SQL时应加入抗倾斜的通用写法

#### 2.4 资源配置与并行度
- **推荐**：启用分区合并：`spark.sql.adaptive.coalescePartitions.enabled=true`
- **推荐**：对于100GB+数据集，初始分区数建议设为200-500
- **推荐**：PySpark场景启用Arrow加速：`spark.sql.execution.arrow.pyspark.enabled=true`

#### 2.5 缓存策略
- **推荐**：仅对频繁访问的中间结果或聚合表使用 `cache()` 或 `persist()`
- **推荐**：使用 `persist(StorageLevel.MEMORY_AND_DISK_SER)` 启用序列化减少内存占用
- **避免**：对整个数据湖或全量数据进行缓存

#### 2.6 JOIN优化
- **推荐**：大表JOIN大表使用Sort Merge Join（Spark默认）
- **推荐**：大表JOIN小表使用Broadcast Join（自动识别或手动HINT）
- **推荐**：确保JOIN键数据类型一致，避免隐式类型转换导致索引失效
- **推荐**：JOIN时遵循“小表在右”原则（如果优化器未自动处理）

#### 2.7 写入目标Paimon表优化
- **推荐**：写入前调整分区数，避免小文件过多：`spark.sql.shuffle.partitions=200`（根据数据量调整）
- **推荐**：使用 `INSERT OVERWRITE` 实现幂等写入，避免 `DROP + CREATE` 的非原子操作
- **推荐**：对频繁更新的场景，利用Paimon的Merge on Read能力，避免全量覆盖

### 三、数据建模与设计规范（整合阿里/美团/字节实践）

#### 3.1 命名规范
- **强制**：表名、字段名使用小写字母+下划线分隔，禁止使用大写字母
- **强制**：表名不使用复数名词
- **强制**：禁止使用数据库保留字作为表名或字段名
- **推荐**：表命名格式：“业务名称_表的作用”，如 `dwd_policy_issue`、`dws_policy_daily`
- **推荐**：布尔型字段使用 `is_xxx` 命名，数据类型为 `tinyint`（1表示是，0表示否）

#### 3.2 字段规范
- **强制**：关联查询的两个字段，数据类型必须一致
- **推荐**：每个表应包含三大必备字段：主键、创建时间、更新时间
- **推荐**：字段含义变更时，及时更新注释
- **推荐**：字段允许适当冗余以提高查询性能，但必须考虑数据一致性

#### 3.3 幂等性设计
- **强制**：ETL任务必须具备幂等性：相同输入重复执行输出恒定，不产生副作用
- **推荐**：使用 `INSERT OVERWRITE` 而非 `DROP + CREATE`，避免非原子操作导致数据丢失

### 四、可维护性与可读性（整合eBay/腾讯实践）

#### 4.1 业务字典与术语统一
- **强制**：对公司已有统一命名的专业术语，必须采用标准命名
- **推荐**：维护业务名词库，统一定义专业概念和术语，注明适用范围
- **推荐**：相似字段名通过数据源、级别名、细分属性加以区分（如 `PARTNER_CLICK`、`INTERNAL_CLICK`）

#### 4.2 数值类型处理
- **强制**：使用 `decimal` 存储小数，禁止使用 `float`、`double`，防止精度损失
- **推荐**：区分原始数值指标（可直接算术运算）与衍生数值指标（不能直接相加）
- **推荐**：定类数据不作为数值指标，不可进行算术计算

#### 4.3 异常处理与边界
- **推荐**：对于可能存在空值的字段，使用 `COALESCE` 或 `NVL` 处理NULL值
- **推荐**：对于聚合操作，明确处理边界条件（如除数为0）
- **推荐**：对于可能存在数据缺失的场景，使用 `LEFT JOIN` 而非 `INNER JOIN` 保留主表记录

#### 4.4 CTE vs 子查询
- **推荐**：复杂逻辑优先使用CTE（WITH AS）而非嵌套子查询，提高可读性
- **推荐**：CTE应命名清晰，反映其业务含义

### 五、安全与合规

#### 5.1 数据权限
- **强制**：禁止在生产环境执行 `DROP TABLE` 或 `TRUNCATE` 等危险操作
- **推荐**：使用 `INSERT OVERWRITE` 替代 `DROP + CREATE` 方式刷新数据

#### 5.2 审计要求
- **推荐**：关键数据操作（如保单支付、理赔审批）应记录操作日志
- **推荐**：敏感字段（如身份证号、手机号）应加密存储或脱敏展示

- 编写新SQL时，对照上述规范逐条检查
- 代码审查阶段，使用本规范作为审查标准
- 对于历史遗留的不规范SQL，逐步重构优化
