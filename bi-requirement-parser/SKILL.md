# BI 需求解析 Skill

## Skill 名称
`bi-requirement-parser`

## Skill 目标
将业务方以自然语言或零散形式提出的需求，通过 **AI主动分析、智能追问、规范术语、反向约束** 四个核心能力，转化为结构化、可执行的 BI 数据需求文档。

**核心亮点**：
- **AI 主动思考**：不是被动等业务说清楚，而是 AI 先分析业务意图，推导需要哪些数据
- **智能追问**：一次性列出所有需要确认的问题，避免反复沟通
- **自动推导**：基于业务描述，AI 主动推荐分析维度和指标
- **端到端**：从一句话需求到代码开发全自动化

## 触发条件
当用户输入包含以下关键词的自然语言描述时触发：
- 核心词：需求、分析、统计、报表、看板
- 动作词：统计一下、分析一下、想知道、看一下
- 对比词：对比、环比、同比、差异

> **跳过条件**：如果用户已按需求模板填写完整内容，直接输出"需求完整，无需解析"。

## 需求类型判断（第一步，所有需求必经）

收到用户输入后，AI **首先判断需求类型**，不同类型走完全不同的流程。

### 类型一：临时取数（轻量级，1-2 分钟完成）

**特征**：一次性查询，个人使用，不需要建表/调度/留存。

**判定规则**（三级判断，详见 `adhoc-query-system.md`）：

| 级别 | 判定方式 | 示例 |
|------|----------|------|
| Level 1 | 命中临时取数关键词（置信度 ≥ 80%） | "帮我取一下最近7天的保单量"、"查一下 TOP10 渠道" |
| Level 2 | AI 语义推断（有"给我/看一下/今天/现在"等词） | "我想要今天的车险报价数据" |
| Level 3 | 人类互动（追问 1 个问题） | "你需要定期看还是查一次就行？" |

**临时取数流程**（不走审批、不建表、不提交 Git）：
```
用户输入 → AI 解析需求 → 确认表和字段 → 查缓存（是否有相同近期查询）
→ 未命中则生成 SELECT SQL → EXPLAIN 验证 → 集群执行 → 返回结果
→ 写入临时取数缓存（记录 fingerprint）→ 检查是否触发提升规则
```

**临时取数输出**：
```markdown
## 临时取数结果

**查询 ID**：ADHOC-20260421-001
**执行的 SQL**：（展示 SQL）
**查询结果**：（展示数据表格）
**执行耗时**：3.2 秒 | **结果行数**：10 行

---
💡 这个查询近30天已被执行 8 次（5人），是否要升级为定期报表？回复"好"自动生成报表需求。
```

> **临时取数不需要**：需求去重、影响分析、人工审批、Git 提交、调度配置。

### 类型二：正式报表（完整流程，5-10 分钟完成）

**特征**：定期产出，多人使用，需要建表、ETL、调度、留存。

**判定规则**：
- 命中报表关键词（"做报表""看板""定期""上线"）
- 或用户在临时取数后主动升级（"做成报表吧"）
- 或临时取数触发提升规则且用户确认

**正式报表流程**：按现有的完整链路执行（见下方处理逻辑）。

### 临时取数 → 报表的自动提升

当临时取数被反复查询时，系统会自动检测模式并建议提升：

| 提升得分 | 触发条件 | AI 动作 |
|----------|----------|---------|
| 15+ 分 | 同一模式被 ≥3人 或 ≥5次查询 | 查询时提示"是否升级为报表" |
| 30+ 分 | 30天内 ≥10次查询 | 主动推送提升建议 |
| 50+ 分 | 持续高频 + 多人 + 复杂 JOIN | 自动生成正式需求文档 |

用户确认后，AI 自动将临时取数转化为正式需求，进入完整流程。

> **详细设计**见 `adhoc-query-system.md`

## 输入模式

本 Skill 支持三种输入方式，自动判断：

### 模式一：聊天窗口输入一句话（v2.0 AI 主动分析模式）

**触发条件**：用户在聊天窗口直接输入一句话或零散想法，信息不完整。

**流程**：AI 主动分析 → 智能追问（最多 3 轮）→ 业务确认 → 生成完整需求文档 → 自动触发下游开发。

**示例**：
- "最近用户流水比较大"
- "看一下车险报价转化率"
- "帮我分析一下退保原因"

### 模式二：@文件 引用完整需求文档（v1.0 直接解析模式）

**触发条件**：用户通过 `@文件名` 引用外部文件，文件中包含需求内容。

**流程**：读取文件内容 → 检查要素完整性 → 如果完整则直接输出结构化需求文档 → 自动触发下游开发；如果有关键缺失则追问补充。

**支持的文件格式**：`.txt`、`.md`、`.docx`

**使用方式**：
```
@requirements.txt
```
或指定处理某个需求：
```
@requirements.txt 处理 C-REQ-003
```
或指定处理一批需求：
```
@requirements.txt 处理 B-REQ-001 到 B-REQ-007
```

**文件内容格式**：
- 文件中可包含**单个需求**或**多个需求**（按 `### 【需求编号】标题` 分隔）
- AI 会自动识别文件中的需求条目，逐个解析
- 如果用户指定了需求编号（如"处理 C-REQ-003"），则只解析指定的需求
- 如果用户未指定，默认解析文件中**所有需求**，逐个输出结构化文档

**示例场景**：

你的 `requirements.txt` 文件中有 20 个需求：
```
### 【C-REQ-001】三免信用赔用户活跃与续保分析报表
...（需求内容）

### 【C-REQ-002】人伤案件医疗垫付时效监控报表
...（需求内容）

### 【C-REQ-003】非车险理赔效率KPI统计报表
...（需求内容）
```

你在聊天窗口输入：
```
@requirements.txt 处理 C-REQ-003
```
AI 读取文件，只解析 C-REQ-003，输出结构化文档并触发开发。

你也可以输入：
```
@requirements.txt 处理全部
```
AI 会逐个解析文件中的所有 20 个需求，每解析完一个就询问是否继续下一个。

### 模式三：聊天窗口粘贴完整需求（v1.0 直接解析模式）

**触发条件**：用户直接在聊天窗口粘贴完整的需求文档内容，信息要素齐全。

**流程**：检查要素完整性 → 如果完整则直接输出结构化需求文档 → 自动触发下游开发；如果有关键缺失则追问补充。

**示例**：
- 用户粘贴了一段结构化的需求描述，如：
  > "统计近30天各渠道的车险保费收入，按日、渠道、险种三个维度，需要日频产出，T+1 8:00前完成，使用 dws_premium_daily 表"

**完整度判断标准**（以下 5 项全部满足则判定为"完整"，直接进入开发）：
1. ✅ 时间范围明确（如"近30天""上季度""2024年1月"）
2. ✅ 分析对象明确（如"车险保费""用户流水""退保订单"）
3. ✅ 关键指标明确（至少一个可量化指标，如"保费收入""流水金额""退保率"）
4. ✅ 分析维度明确（如"按日、渠道、险种"）
5. ✅ 数据来源可识别（表名或业务系统名）

> **两种模式可以随时切换**：如果多轮对话过程中用户直接提供了完整信息，立即切换为模式二输出最终文档。

## 输入格式
业务方任意形式的自然语言描述（口头、邮件、聊天记录、会议纪要等）。

```markdown
### 【需求编号 v{version}】需求标题

**需求状态**：草稿 → 已确认 → 开发中 → 验收中 → 已上线

（原样保留业务方的输入，不加修改）

**2. 需求背景**  
（基于原始描述提炼，如缺失则标注 [待业务确认]）

**3. 一句话需求**

**7. 优先级与排期**
```

## 处理逻辑（Skill 内部执行顺序）

> **重要**：以下处理逻辑仅适用于**正式报表**类型的需求。如果是临时取数，走上面的轻量级流程。

### 第零步：AI 主动分析（核心新增）

当业务方输入一句话需求后，AI 需要先**主动思考**以下内容，而不是直接输出模板：

#### AI 思考框架

```
业务原始输入 → AI 分析以下维度 → 输出"AI 分析报告" + "追问清单"
```

**AI 需要主动思考的问题：**

| 思考维度 | AI 自问 | 示例（业务说"最近用户流水比较大"） |
|----------|---------|--------------------------------------|
| **业务意图** | 业务真正想知道什么？ | 是想知道流水变大的原因？还是想知道影响？还是想做预警？ |
| **分析对象** | 需要分析哪些实体？ | 用户、订单、商品、渠道、时间 |
| **数据需求** | 需要哪些数据来支撑分析？ | 用户流水表、订单表、用户画像表、渠道表 |
| **对比维度** | 需要和什么对比才能发现原因？ | 环比（上周vs本周）、同比（去年vs今年）、分渠道对比 |
| **下钻路径** | 如果发现异常，需要逐层拆解到哪一步？ | 总流水 → 分渠道 → 分商品 → 分用户类型 |
| **根因假设** | 可能导致这个现象的原因有哪些？ | 活动促销、季节因素、系统异常、竞争对手 |
| **缺失信息** | 还需要业务确认哪些关键信息？ | "大"的定义？时间范围？是否需要预警？ |

#### AI 分析报告输出格式

```markdown
## AI 分析报告

### 1. 业务意图理解
您提到"用户流水比较大"，我理解您想分析的是：
- 用户交易流水金额近期的异常增长情况
- 需要定位增长的具体原因（渠道？商品？用户群？）

### 2. AI 推荐的分析方案

**分析路径**：
```
总流水趋势（近30天） → 环比/同比对比 → 分渠道拆解 → 分商品拆解 → 分用户群拆解
```

**可能需要的指标**：
| 指标 | 说明 | 单位 |
|------|------|------|
| 日均流水金额 | 衡量"大"的基准 | 分 |
| 环比增长率 | 本周vs上周变化 | % |
| 渠道流水占比 | 各渠道贡献比例 | % |
| TOP10 商品流水 | 哪些商品贡献最大 | 分 |
| 新客vs老客流水 | 哪类用户贡献大 | 分 |

**可能需要的维度**：
时间（日）、渠道、商品类目、用户等级、地区

### 3. AI 对根因的初步假设
根据经验，流水变大可能是以下原因：
1. 📈 营销活动（近期是否有促销/优惠券活动？）
2. 📅 季节性因素（是否是业务旺季？）
3. 👥 新用户增长（是否有拉新活动？）
4. 💰 单客金额提升（客单价是否上升？）
5. ⚠️ 系统重复计算（是否存在重复交易？）

### 4. 需要您确认的问题（请逐条回复）

**关键问题（必答）：**
1. "流水大"具体是什么情况？是金额比之前多了？还是交易笔数多了？还是两者都多？
2. 您希望分析的时间范围是？近7天？近30天？近3个月？
3. "流水"指的是哪个系统的数据？支付系统？订单系统？银行流水？

**补充问题（选答，不答我会使用默认值）：**
4. 需要分渠道分析吗？（默认：是）
5. 需要建立预警机制吗？还是一次性分析？（默认：一次性分析）
6. 优先级和期望完成时间？

> 请回复问题编号+答案，例如："1是金额多了 2近30天 3支付系统"
```

#### 多轮对话流程

```
业务输入："最近用户流水比较大"
    ↓
AI 第1轮：输出分析报告 + 追问清单（最多5个问题）
    ↓
业务回复："1金额多了 2近30天 3支付系统 4需要分渠道"
    ↓
AI 第2轮：更新需求文档 + 补充追问（如果有新问题）
    ↓
业务回复："确认"
    ↓
AI 最终轮：输出完整需求文档 v1.0
    ↓
自动触发 requirement-diff-analyzer(mode=new/upgrade) → 审批门禁 → sql-code-generator → sql-validator → cluster-tester → git-merger → scheduler-updater
```

### 第一步：识别缺口
- 基于第零步的 AI 分析，确认业务回复后，检查以下要素是否完整：
  - 时间范围（如"最近一个月""上季度"）
  - 核心分析对象（用户、订单、保单、活动等）
  - 关键指标（至少一个可量化的数值）
  - 对比基准（环比、同比、分组对比等）
  - 验收标准（如何验证、何时产出）
- 对每个缺失项，在输出中标记 `[待业务确认]`，并在输出末尾生成 **追问清单**：
  ```markdown
  **请补充以下信息：**
  1. 时间范围：您希望统计哪段时间的数据？
  2. 对比基准：是否需要与某个群体或历史时段对比？
  3. 验收方法：如何判断计算结果正确？
  ```

### 第二步：规范术语
- 将模糊词汇转化为可量化指标（规则如下）：

| 业务方说的 | 转化为 |
|------------|--------|
| 很多用户、大量 | 具体数值阈值（如 >1000 人）[待业务确认阈值] |
| 很多、不少、不少 | 具体数值（如 >1000 人）[待业务确认阈值] |
| 增长好、表现好、不错 | 环比增长率 ≥X% [待业务确认阈值] |
| 下滑、下跌、下降 | 环比增长率 <0% [待业务确认] |
| 很快、很慢 | 具体时长（如 <5 分钟）[待业务确认阈值] |
| 活跃、不活跃 | 近30天登录天数 ≥X 天 [待业务确认 X] |
| 高价值、优质、头部 | 保费金额 ≥X 分 [待业务确认 X] |
| 低价值、尾部 | 保费金额 <X 分 [待业务确认 X] |
| 近期、最近 | 近7天/30天/90天 [待业务确认] |
| 大多数、普遍 | 比例 ≥X% [待业务确认阈值] |
| 少数、个别 | 比例 <X% [待业务确认阈值] |

- 统一单位：金额用"分"，时间用"天/小时/秒"，比率用"%"，用户数用"人"。
- 如果业务给了数据库表名、字段名、SQL 关键字，可以输出供开发参考

### 第三步：自动匹配数据源表（核心步骤）

> **此步骤强制执行，不可跳过。AI 必须主动查询数据字典，不能被动等待人工确认。**

#### 3.1 执行流程

```
需求中的业务概念 → 读取数据字典 → 语义匹配表名+字段 → 输出匹配结果
```

#### 3.2 数据字典查询（RAG 语义检索，优先使用）

**方式 A：RAG 检索（推荐，最省 Token）**

如果服务器上存在 RAG 索引目录，AI **必须**使用此方式：

```
RAG 索引目录: /home/openclaw/.openclaw/workspace/dict_rag_index/
├── index.faiss    ← FAISS 向量索引
├── idmap.pkl      ← 表名映射
├── tables.json    ← 完整表结构数据
└── domains.json   ← 域信息
```

> **RAG 检索流程**：
> ```
> 需求描述（如"三免信用赔用户活跃度续保分析"）
>   ↓ 调用 rag --search "需求关键词" --top-k 5
> 返回 Top-5 最相关的表（含表名、注释、主键、字段列表、相似度分数）
>   ↓ 只对命中的表读 tables.json 获取完整字段定义
> 输出匹配结果（3-5 张表的完整信息，~5K-10K token）
> ```

> **Token 消耗对比**：
> | 方式 | 每次消耗 | 说明 |
> |------|----------|------|
> | 读 data_dictionary.yaml 全文 | ~35K token (126KB) | ❌ 禁止 |
> | 读索引 + 域文件 | ~22K token (8KB索引 + 2个域) | 可用 |

### 第七步：需求去重与版本管理（自动执行）

在需求文档生成后、任何代码动作之前，AI 必须执行需求去重检查。

#### 7.1 需求状态判定

AI 需要将当前需求与**已有需求库**进行比对，判定为以下三种状态之一：

| 状态 | 判定条件 | 处理方式 |
|------|----------|----------|
| **新增需求** | 与所有已有需求的核心对象+指标+维度均不同 | 分配新需求编号，版本 v1.0，继续开发 |
| **升级需求** | 核心对象相同，但指标/维度/口径有变化 | 保留原需求版本，新版本号 +1，进入影响分析 |
| **重复需求** | 核心对象+指标+维度+口径完全相同 | 拒绝，提示已有需求编号 |

#### 7.2 判定规则

**"核心对象"** = 需求中分析的业务实体（如"车险保费""用户流水""退保订单"）

比对优先级（按严格程度递减）：
1. **精确匹配**：需求编号相同（如 `@requirements.txt 处理 C-REQ-003`，而 C-REQ-003 已存在）→ 升级需求
2. **语义匹配**：核心对象 + 关键指标 + 分析维度三者组合相似度 ≥ 80% → 升级需求
3. **完全不同**：核心对象不同，或相似度 < 50% → 新增需求

#### 7.3 版本号管理

```
新增需求：C-REQ-021 v1.0（全新）
升级需求：C-REQ-003 v1.0（原版保留，不修改）
          C-REQ-003 v2.0（升级版，新建）
          C-REQ-003 v3.0（再次升级，新建）
```

**关键规则**：
- 升级需求和原需求**共存**，原需求的代码、表结构、调度不受影响
- 升级版本号递增：v1.0 → v2.0 → v3.0
- 每个版本的代码提交到**独立的版本分支**（如 v0.0.1 对应 C-REQ-003 v2.0）

#### 7.4 输出格式

```markdown
## 需求去重检查

**当前需求**：C-REQ-003 非车险理赔效率KPI统计报表
**检查结果**：⚡ 升级需求（核心对象相同，指标口径有变化）

**已有版本**：
| 版本 | 状态 | 变更说明 |
|------|------|----------|
| v1.0 | 已上线 | 按季度统计结案周期和自动核赔率 |
| v2.0 | 本次 | 新增"按案件类型下钻"维度 |

**版本关系**：v2.0 与 v1.0 共存，v1.0 的代码和调度不受影响。
```

**重复需求时输出**：
```markdown
## 需求去重检查

**当前需求**：C-REQ-003 非车险理赔效率KPI统计报表
**检查结果**：🔴 重复需求

**已存在的相同需求**：C-REQ-003 v1.0（已于 2025-03-15 上线）

**建议**：
- 如需修改，请使用升级模式（说明需要调整的内容）
- 如需查看已上线需求的详情，请告知
```

## 注意事项
- **需求类型优先判断**：收到任何输入后，首先判断是临时取数还是正式报表，走不同流程。临时取数走轻量级路径（不审批、不建表、不提交 Git），正式报表走完整链路。
- **三种输入方式**：聊天窗口一句话（v2.0 多轮对话）、聊天窗口粘贴完整需求（v1.0）、@文件引用需求文档（v1.0），AI 自动判断切换。@文件方式支持指定需求编号，可逐个或批量处理。
- **临时取数缓存与提升**：所有临时取数都会记录到缓存，通过查询指纹进行模式匹配。高频临时取数自动检测并建议提升为正式报表（详见 `adhoc-query-system.md`）。
- **需求去重**：每次解析需求后必须执行去重检查，区分新增/升级/重复三种状态。升级需求保留原版本，新建升级版本号。
- **审批门禁**：写代码之前必须输出影响分析报告并等待人工审批。审批不通过绝不写代码、不验证、不提交。这是硬性门禁，不可跳过。
- **两道人工确认**：第一道是影响分析审批（写代码前），第二道是 Git 合并确认（验证通过后）。
- **AI 优先思考**：收到需求后，AI 先分析业务意图，推导需要的数据，再输出追问清单。不要让业务自己想需要什么数据。
- **追问精简**：每轮追问不超过 **5 个问题**，问题应该简洁明确，给出选项而非开放题。
- **默认值策略**：选答题不回答时，AI 使用合理默认值并标注，减少沟通成本。
- **端到端自动**：业务确认后，后续开发、测试、提交全部自动完成，无需人工介入。
- 如果业务已按模板提供完整需求，直接进入开发流程，跳过多轮对话。
- 严禁在输出中臆测缺失信息，所有不确定处必须标记 `[待业务确认]` 并生成追问清单。
- 最多追问 **3 轮**，超过限制建议线下补充。
- **保守原则**：AI 无法判断需求类型时，默认走临时取数流程（避免过度建设）。用户可随时手动升级为报表。
- **SQL 知识库（动态积累）**：
  - **查询时机（写SQL前）**：审批通过后必须先查 `kb search -r "关键词" --top-n 5`，获取历史经验
  - **入库时机（验证后）**：SQL 验证通过/失败后**自动入库积累经验**
    - 验证通过: `kb add --type correct --sql "SQL文本" --requirement "需求描述"`
    - 验证失败: `kb add --type error --sql "SQL" -e "错误信息" --correct-sql "修正版" -l "教训总结"`
  - **初始为空**：首次使用时知识库是空的，随着使用次数增加越来越准
  - 所有 Python 脚本统一通过快捷入口执行（`kb` / `rag`），内部自动处理虚拟环境
